How delivery works

  1. Register — one database transaction locks the workshop row, inserts the registration (unique per member) and the confirmation outbox event, then commits. The HTTP response never waits for delivery.
  2. Claim — workers claim due events with SKIP LOCKED + a lease token. Expired leases are reclaimed after crashes.
  3. Send — the worker POSTs to the mock service with the event id as Idempotency-Key, outside any DB lock.
  4. Settle — success marks DELIVERED; transient failures retry with capped full-jitter backoff (forever); permanent failures park as NEEDS_ATTENTION.
  5. Deduplicate — the receiver keeps durable receipts; resends of the same key+payload succeed without creating a second receipt.

Fault modes

  • always_success — healthy service.
  • fail_first_n — first N requests get 503, then success (retry demos).
  • always_503 — persistent transient failure (scoped demos).
  • always_400 — permanent failure → NEEDS_ATTENTION.
  • timeout_before_commit — hangs past the client timeout, writes no receipt.
  • commit_then_timeout — writes the receipt, then loses the response (ambiguous outcome).
  • seeded_random — seeded PRNG with a recorded seed.
